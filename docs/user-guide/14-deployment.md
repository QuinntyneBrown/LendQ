# Deployment

This page explains how LendQ is deployed — environments, CI/CD pipelines, and the manual knobs you reach for when something goes sideways.

For the architectural rationale (why Container Apps instead of AKS, etc.) see [Azure Cheapest Deployment](../azure-cheapest-deployment.md) and [Azure Deployment Plan](../azure-deployment-plan.md).

## Environments

LendQ uses two long-lived environments:

| Environment | Purpose | Deploys on | Base URL (example) |
|---|---|---|---|
| **Staging** | Pre-production testing, demo data | every push to `main` | `https://lendq-api-staging.<azcontainerapps>.io/api/v1` |
| **Production** | Real users | manual `workflow_dispatch` | project-specific |

Preview environments for pull requests are produced automatically by Azure Static Web Apps for the frontend.

## Hosting stack

- **Frontend** — Azure Static Web Apps (Free or Standard plan).
- **Backend API** — Azure Container Apps (Consumption plan).
- **Worker / Beat** — additional Container Apps (staging only by default).
- **Database** — Azure Database for PostgreSQL Flexible Server (Burstable).
- **Container registry** — Azure Container Registry (`lendqacr`).
- **Migrations** — Azure Container Apps Job (`lendq-migrate-staging`).
- **Static Web App** — `swa-lendq-staging`.

Infrastructure is Bicep-defined in [`ops/azure/`](../../ops/azure):

- `main.bicep` — top-level orchestrator
- `main.staging.bicepparam` — staging parameter file
- `main.production.bicepparam` — production parameter file
- `modules/` — per-service modules

## CI/CD overview

Three GitHub Actions workflows live in [`.github/workflows/`](../../.github/workflows):

| Workflow | File | When |
|---|---|---|
| Deploy to Staging | `deploy-staging.yml` | push to `main`, manual `workflow_dispatch` |
| E2E (pull request) | `e2e-pr.yml` | on PR |
| E2E (full matrix) | `e2e-full.yml` | nightly / manual |

### Deploy to Staging — what it does

1. **Checkout** repo.
2. **Azure login** with OIDC credentials (stored as `secrets.AZURE_CREDENTIALS`).
3. **Log in to ACR**.
4. **Build and push** the backend Docker image tagged with the commit SHA and `latest`.
5. **Update Container Apps** for API, worker, and beat — each `az containerapp update --image …`.
6. **Run database migrations** via a Container Apps Job; polls for success (60 × 10s retries).
7. **Verify API health** — `curl /api/v1/health/ready` with a 30×5s retry loop.
8. **Ensure staging env vars** on the API (seed profile, rate limits).
9. **Deploy the frontend**:
   - `npm ci` and `npm run build` in `frontend/`.
   - `VITE_API_BASE_URL` is baked in at build time (hardcoded in the workflow).
   - `Azure/static-web-apps-deploy@v1` uploads `frontend/dist` using the `SWA_DEPLOYMENT_TOKEN_STAGING` secret.

Typical run time: ~6–10 minutes.

### GitHub secrets required

Defined in the workflow file and recorded in [`ops/azure/github-secrets-setup.txt`](../../ops/azure/github-secrets-setup.txt):

- `AZURE_CREDENTIALS` — JSON service principal with access to the staging resource group.
- `SWA_DEPLOYMENT_TOKEN_STAGING` — deployment token generated by the Static Web App resource.

## Manual deploy

Trigger the workflow manually via the GitHub UI:

1. Go to **Actions** → **Deploy to Staging**.
2. Click **Run workflow** → pick the branch → **Run workflow**.

Or via the `gh` CLI:

```bash
gh workflow run deploy-staging.yml --ref main
```

## Deploying to production

Production currently has no automated workflow. To deploy to production today:

1. Update the image tag in ACR for the production Container App:

   ```bash
   IMAGE_TAG="<sha-or-tag>"
   az containerapp update \
     --name lendq-api-prod \
     --resource-group rg-lendq-prod \
     --image lendqacr.azurecr.io/lendq-api:$IMAGE_TAG
   ```

2. Run the production migration job:

   ```bash
   az containerapp job start \
     --name lendq-migrate-prod \
     --resource-group rg-lendq-prod
   ```

3. Monitor execution:

   ```bash
   az containerapp job execution list \
     --name lendq-migrate-prod \
     --resource-group rg-lendq-prod \
     --query "[0].properties.status" -o tsv
   ```

4. Verify health:

   ```bash
   curl https://<prod-fqdn>/api/v1/health/ready
   ```

5. Deploy the frontend:

   ```bash
   cd frontend
   npm ci
   VITE_API_BASE_URL=https://<prod-api-fqdn>/api/v1 npm run build
   az staticwebapp deploy \
     --name swa-lendq-prod \
     --resource-group rg-lendq-prod \
     --source dist \
     --env production
   ```

## Rolling back

### Backend

List recent revisions:

```bash
az containerapp revision list \
  --name lendq-api-staging \
  --resource-group rg-lendq-staging \
  --query "[].{name:name,active:properties.active,created:properties.createdTime}" \
  --output table
```

Activate the previous revision:

```bash
az containerapp revision activate \
  --name lendq-api-staging \
  --resource-group rg-lendq-staging \
  --revision <previous-revision-name>
```

### Frontend

Azure Static Web Apps retains deployment history. Re-deploy a previous commit by pushing a revert:

```bash
git revert <bad-commit-sha>
git push origin main
```

The staging workflow rebuilds the frontend from the reverted tree.

## Environment variables

The API picks up most config from environment variables. Key ones:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `SECRET_KEY` | Flask session key |
| `JWT_SECRET_KEY` | JWT signing key |
| `REDIS_URL` | Celery broker URL. `memory://` disables Redis entirely. |
| `CORS_ORIGINS` | comma-separated allowed origins |
| `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD` | SMTP settings |
| `SEED_ON_STARTUP` | `baseline`, `demo`, or empty |
| `RATELIMIT_DEFAULT` | Flask-Limiter default |
| `RATE_LIMIT_AUTH` | login/signup-specific limit |
| `LOG_LEVEL` | `INFO`, `DEBUG`, etc. |
| `LOG_FORMAT` | `json` for production, `text` for local |

See [`ops/azure/main.staging.bicepparam`](../../ops/azure/main.staging.bicepparam) for the full set applied to staging.

## Health endpoints

The API exposes:

- `GET /api/v1/health/live` — liveness (just confirms the process is up).
- `GET /api/v1/health/ready` — readiness (checks DB, and Redis if enabled).

The staging deploy workflow probes `/health/ready` as its post-deploy gate.

## Observability

- **Logs** — Container Apps log stream accessible via `az containerapp logs show` or the Azure portal.
- **Application Insights** — if configured, traces and metrics are in the linked App Insights resource.
- **Request IDs** — every API response includes `X-Request-ID` header; forward it in bug reports so backend logs can be correlated.

## Troubleshooting deploys

| Symptom | Cause | Fix |
|---|---|---|
| Workflow fails at "Log in to ACR" | `AZURE_CREDENTIALS` secret expired or revoked | Regenerate the service principal; update the secret. |
| Migration job times out | Long migration, or worker pod never started | Check job execution logs; consider splitting the migration. |
| Health check fails after deploy | API failed to start (usually bad env var or broken migration) | `az containerapp logs show --name lendq-api-staging --resource-group rg-lendq-staging`; fix env and redeploy. |
| Frontend build succeeds but shows stale API URL | `VITE_API_BASE_URL` is baked at build time, not runtime | Update the workflow file with the new URL and re-run. |
| `Ensure staging env vars` step fails | Container App is still rolling | It has `continue-on-error: true`; the deploy succeeds even if this step is racy. Re-run the workflow to apply env var updates. |

For app-level errors after a successful deploy, see [Troubleshooting](16-troubleshooting.md).
